# 동적 판단이 필요한 두 곳(법률 분석·감사)만 도구 사용 에이전트로 두고, 나머지는 결정적 도구와 검증기로 둔다

선형 파이프라인을 노드로 쪼갠다고 멀티 에이전트가 되지는 않는다. 무엇을 검색하고 어느 조문을 읽고 언제 질문하고 언제 끝낼지가 상태에 따라 달라지는 곳은 법률 분석(Legal Analyst)과 사용자 수정 뒤의 재검증(Auditor)뿐이다. 이 둘만 `create_agent` 기반 도구 호출 루프로 만들고, 지각·검색·렌더·검증은 입력이 같으면 출력이 같은 결정적 도구로 유지한다. 에이전트 출력은 결정적 검증기(인용 존재·표기 일치·시행일·요건 파생)와 커버리지 점검을 통과해야 하며, 도구 호출·검색·질문 라운드·재시도에 예산이 있고 소진 시 불확실 표시로 강제 종료한다.

## Considered Options
- 워크플로 + LLM 단계(v1 초안): 질문·검색 순서가 고정돼 새 쟁점에 대응하지 못함.
- 단일 자율 에이전트(모든 도구): 가장 유연하지만 긴 궤적에서 환각·누락을 검증하기 어렵고 비용을 예측할 수 없음.
- 규칙 엔진 + LLM 설명: 규칙 밖 대응 불가. 실험 베이스라인으로만 구현.

## Consequences
- 평가는 노드 단위 지표에 더해 에이전트 궤적 지표(도구 호출 수, 질문 수, 커버리지 경고율, 인용 유효율)를 함께 본다.
- 사용자 질문은 에이전트의 `ask_user` 도구가 `interrupt()`로 구현되므로 체크포인터가 필수이고, interrupt 앞의 부수효과는 멱등이어야 한다.
