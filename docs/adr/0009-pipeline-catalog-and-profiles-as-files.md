# 프로필은 부품마다 후보 하나를 고른 조합이고, 부품 카탈로그·프로필·서비스 포인터는 `configs/pipeline/`의 YAML 파일이다. 실험실은 같은 파일을 읽고 쓴다

프로필은 파이프라인의 교체 가능한 부품(지각 · 장면 이해 VLM · 법률 검색 · 에이전트 LLM · 렌더, 27개)마다 카탈로그 후보 하나를 고르고 예산 · 설정 12개를 정한 조합이다. 후보 전체는 `configs/pipeline/catalog.yaml` 한 파일에 근거(R1~R7)와 함께 모으고, 프로필은 `profiles/<id>.yaml`, 서비스가 쓰는 프로필은 `service.yaml`에 둔다. 실험실은 이 파일들을 바뀔 때마다 다시 읽고, 화면에서 만든 프로필 · 추가한 후보 · 서비스 적용을 같은 파일에 기록한다. 화면에서 추가할 수 있는 후보는 **이미 등록된 어댑터 계열의 다른 모델**뿐이다(OpenRouter 모델은 공개 모델 목록에서 단가와 기능을 채움). 구조가 다른 새 계열은 어댑터 코드를 먼저 구현해야 하므로 파일에서만 등록한다. 서비스 적용은 현재 config_hash로 회귀 게이트를 통과한 실험이 있어야 한다.

## Considered Options
- 후보를 코드(TypeScript/Python 상수)에 둔다: 한 언어에서만 읽히고, 화면에서 추가하면 소스 파일을 고쳐야 한다.
- 후보를 데이터베이스에 둔다: 팀이 git으로 검토할 수 없고, 코드 리뷰 없이 실행 조합이 바뀐다.
- 화면에서 어떤 모델이든 추가: 어댑터가 없는 계열은 실행할 수 없어 "추가됐지만 못 돎" 상태가 생긴다.
- 기존 `configs/*.yaml` 형식 확장: 옛 백엔드가 폴더의 모든 YAML을 프로필로 읽어 카탈로그가 프로필로 오인된다. 새 형식은 하위 폴더에 둔다.

## Consequences
- M4 백엔드는 같은 파일을 읽어 부품마다 어댑터를 고르고, `config_hash`(후보 ID · 파라미터의 해시)를 실행 · 실험 메타데이터로 LangSmith에 남긴다(NFR-04).
- 화면 편집이 파일 형식을 흐트러뜨리지 않도록 직렬화 옵션을 손으로 쓴 파일과 맞췄다(읽고 다시 쓴 결과가 원본과 같음). 테스트는 임시 사본(`PRIVFRAME_PIPELINE_SANDBOX=1`)에서 돌아 저장소 파일을 바꾸지 않는다.
- M2 모의 엔진은 프로필 선택을 공개된 규칙(`frontend/mock/flow.ts`의 `MOCK_RULES`)으로 동작에 반영한다. 이 규칙은 화면 검수용 가정이며, M4부터는 실제 부품이 결과를 만든다.
- OpenRouter 목록 단가는 제공자 · 시점에 따라 달라질 수 있어, 후보마다 출처와 날짜를 근거 메모에 남긴다.
